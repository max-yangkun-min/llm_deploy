# KV 上限反向提示(这张卡最多能开多长)

- 功能 ID:`kv-max-context`
- 状态:`已完成`
- 创建:`2026-09-18`
- 最后更新:`2026-09-18`
- 对应任务记忆:`.agents/tasks/deploy-portal/MEMORY.md`

## 意图

给选型的人回答一个正向核算答不出来的问题:**「就用这些卡、这个档,上下文最多能开到多长」**。

现在平台只会正着算:你填 `context_k`,它算出 KV 要多少显存、放不放得下。于是「放不下」
只说得出「单卡超过可用显存」,说不出**差在哪**;而真正要下单的人想知道的是
「8 张 A100 跑 GLM-5.2-INT4,能开到 1024K 吗?开不到的话最多多少?」——
这是容量规划,不是填表校验。

## 现状

`model-selector/recommend.py` 里上下文是**输入**:`assess()` 取
`wanted_context = hw.get("context_k") or hw.get("min_context_k")`,再
`kv_gib(row, context_used)` 正算。没有任何地方反算。

实测(2026-09-18,`assess()` 的输入输出):

| 事实 | 证据 |
|---|---|
| 上下文只进不出 | `recommend.py:227` 读入、`:232` 选默认,没有任何反向求解 |
| 超限时的说明只说得出「显存不够」 | `:258` 的失败信息是「单卡需 X GiB(权重+KV+余量),超过 Y GiB 卡的可用 Z GiB」,与「上下文要太长」和「权重本身就装不下」是同一条 |
| 上限其实是可反算的 | `kv_gib()` 对 context 是**线性**的(`elems × layers × tokens × 2B`),把同一条公式倒过来就是 KV 的可用余量能换成多少 K |
| 有些档反算不出来,而且必须留空 | `llama31-405b-bf16` 的 `kv_elems_per_token_per_layer` / `attention_layers` 为空(config 全 401),`kv_gib()` 已经如实返回 `None`;这类档同样反算不出 |
| 昇腾是另一回事 | 非 CUDA 卡上 KV 精度由 `--quantization ascend` 的专有量化决定,**没有可核实的公开公式**,现有代码已因此把 `kv_gib` 置 `null` + 说明 |

## 验收标准

- [x] `/api/recommend` 的每个 plan 的 `memory` 里增加 `max_context_k`;算不出时必须是
      `null`,并且 `max_context_note` 非空、写明**为什么**算不出(不许编一个数)。
- [x] CUDA 卡 + KV 结构已核实的档:`max_context_k` 是正整数,且与正向核算自洽——
      用它算出的 `per_card_gib` 不超过 `vram × PER_CARD_BUDGET`,而 `max_context_k + 1`
      就超了。
- [x] 用户填的上下文超过显存反算上限时,判定变成「放不下」,且失败信息里
      **指明是 KV 超了**(而不是与「权重装不下」共用同一条)。
- [x] 昇腾卡:`max_context_k` 为 `null` + 下界说明,与现有 `kv_gib = null` 的口径一致。
- [x] 该档自身标称上下文更紧时,取标称值,并在说明里点明是哪一边在限制。
- [x] `smoke_test.py` 补断言,含昇腾 `null` 分支与「自洽性」断言。(112 → 120 项)

> 验收标准第三条的判据实现时改成「超过**显存反算值**」而不是「超过 `max_context_k`」:
> 后者可能被该档标称上下文压住,拿它当判据会把「其实显存够、是模型开不了那么长」跟成
> 「KV 超了」——一句看着精确的错话。这是实现过程中发现并修正的误报,记在这里以免下次又按字面实现。

## 边界:明确不做什么

- **不为算不出的档编一个数。** 结构缺失(如 405B 的 gated config)或非 CUDA 时一律 `null`
  + 说明,和 `kv_gib` 的口径保持一致。
- **不引入新的工程系数。** 反算复用 `PER_CARD_BUDGET` / `RUNTIME_OVERHEAD` / `KV_DTYPE_BYTES`,
  否则正算与反算会用两套假设,页面自相矛盾。
- **不把反算值当成「实测可开到」。** 它是按同一条公式在 92% 显存占用下的上界;
  vLLM 的 KV block 粒度、碎片、并发都会让它更低。说明里要写清这是**上限**。
- **不改 `--max-model-len` 的输入语义。** 用户仍然可以填需求上下文,只是现在填超了
  能得到一句解释。
- **不改 `sm_xx` / 昇腾口径**,不做 KV `fp8` 输入项(R4 另立)。

## 依赖与前提

- `kv_elems_per_token_per_layer` 与 `attention_layers` 由 `sync_hf.py` 从真实 config 抓取,
  已有 18/19 个档可用。
- 显存与卡数来自已核实的 GPU 目录(不接受调用方自填)。
- 无需联网、无需新数据文件。

## 风险

- **算错会误导选型**:反算错了会让人以为能开 1024K 而实际开不到。用「自洽性」断言钉住:
  `max_context_k` 必须放得下、`max_context_k + 1` 必须放不下(同一个公式正反各算一次)。
- **把「标称上限」当成「显存上限」**:有的档 `context_source = card`(模型卡标称,
  需打开 YaRN 等扩展),取它当上限时必须点明来源,不能与显存反算值混为一谈。
- **昇腾上套 CUDA 公式**:那会给出一个看着精确的错数;断言直接要求它为 `null`。
