# 规范驱动开发(SDD)工作区

这个目录放**功能规范**:在动代码之前,先把「要解决什么、什么算做完、边界在哪」
写下来。目的是避免「一边聊一边改、改完说不清改了什么」——尤其是当改动分散在
后端规则、前端渲染、数据目录和文档四处的时候。

## 为什么这个仓库需要它

管理台的规则只有一份实现(`model-selector/recommend.py`),但一次功能改动通常
会同时碰到:

- 规则层(`recommend.py` 的判定与核算)
- 适配层(`deploy-portal/engine.py` 的组装与生态过滤)
- 接口层(`deploy-portal/server.py` 的入参校验)
- 数据层(`data/*.json`、`model-selector/*.csv`)
- 界面层(`web/js/views/*.js` 的显示口径)
- 门禁(`tools/smoke_test.py` 的断言)

没有规范时,最容易漏掉的恰恰是最后一层:代码改对了,但没有断言钉住,下次改别处
又退回去。所以本仓库的规范里,**「验收」一节必须列出会新增哪些断言**。

## 目录约定

```
.codex-specs/
├── README.md                 本文件:流程与模板说明
├── _TEMPLATE/
│   ├── spec.md               功能规范模板
│   └── plan.md               实现计划模板
└── <feature-id>/
    ├── spec.md               这个功能要解决什么、验收标准、边界、不做什么
    └── plan.md               怎么落地:改动清单、顺序、风险、回滚
```

`<feature-id>` 用小写连字符,和 `.agents/tasks/<task-id>/` 保持一致,便于互相对应。

## 流程

1. **写 `spec.md`**:意图、现状、验收标准、边界(明确不做什么)。
2. **写 `plan.md`**:按文件列出要改什么、按什么顺序改、怎么验证、怎么回滚。
3. **改代码**,每完成一步就跑一次 `python tools/ci.py`。
4. **补断言**:把「验收标准」逐条变成 `smoke_test.py` 里的 `check(...)`。
5. **收尾**:更新 `DEVELOPMENT.md` 的阶段进度,把这份 spec 的状态改成 `已完成`。

## 状态字段

`spec.md` 顶部的 `状态` 只有四种,别含糊:

- `草稿` — 还在讨论,不要照着改代码
- `已确认` — 可以开始实现
- `实现中` — 代码在改,但验收标准还没全部满足
- `已完成` — 验收标准全部有断言覆盖,且 `python tools/ci.py --online` 通过

## 两条硬要求

**「不做什么」必须写。** 一份没写「不做什么」的规范,等于没有边界,实现时会
顺手把附近的东西一起改掉。本仓库的例子昇腾那条规范里明确写了「不做 sm 映射」
「不合并两种容量」——这些正是最容易「顺手优化」掉的地方。

**验收标准必须可执行。** 写成「页面显示正确」没法验收;写成「`/api/recommend`
返回的每个 plan 的 `memory.kv_gib` 为 `null` 且 `kv_note` 非空」才能变成断言。
