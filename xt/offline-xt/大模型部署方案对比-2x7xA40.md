# XT · 14×A40 双机部署方案对比与实施(7+7 / 8+6)

> 硬件:2 台服务器,每台 2× Xeon Gold 5320 / 512GB DDR4 / 合计 **14× Tesla A40 48GB** / 双光口万兆(82599);默认 7+7,可选调整为 8+6
> 用途:blade_agent 智能体系统 —— 写 skill / 调 skill / 代码生成(agentic coding)为核心
> 本文给出 **3 个 7+7 主方案 + 1 个 8+6 备用方案**,含对比与部署实施。

---

## 〇、先记住三条硬约束(所有方案的地基)

| 约束 | 内容 | 后果 |
| ---- | ---- | ---- |
| **带宽** | A40 是 GDDR6,**696 GB/s**(仅 A100 的 34%),无 FP8/FP4(Ampere sm_86) | 解码是访存瓶颈:**低激活 MoE 是唯一正解**;激活越大越慢 |
| **7 卡奇数** | 默认 7+7 时,TP 通常取 **1/2/4**,每台必有零头 | 可跨机 PP,或改成 8+6 让一台形成完整 8 卡资源池 |
| **跨机仅 10GbE** | 82599 万兆,聚合也才 ~5GB/s vs NVLink 600GB/s | **跨机 TP 不可行**;跨机只能走 **PP(流水线并行,只传层间激活)** 或 **各跑各的 + 负载均衡** |

> **内核红线**:A40 无稀疏注意力内核。**MLA / Gated DeltaNet / Lightning / 标准注意力 = 能跑**;**DSA / CSA / HCA / IndexShare 稀疏注意力(GLM-5.2、DeepSeek-V4/V3.2)= 出局**(A100 上都只有个位数 tok/s)。

> **PP 是本文两个"单一强模型"方案的关键**:跨机 TP 每层都要 all-reduce,10GbE 扛不住;而 PP 只在流水线切点传一次层间激活,10GbE 能接受。这样两台的 672GB 显存池起来,能装下单台装不下的更强模型。

## 一、三个主方案总览(默认 7+7,能力效果从强到弱)

| 维度 | 🥇 **方案一 · Kimi K2.6(PP)** | 🥈 **方案二 · Qwen3.5-397B(PP)** | 🥉 **方案三 · M2.7 双副本** |
| --- | --- | --- | --- |
| **一句话** | 两台合成开源最强 agentic 大脑 | 两台合成一个稳的强大脑 | 最简最快,一个模型两副本 |
| **模型** | Kimi K2.6(1T / **32B 激活**,MLA) | Qwen3.5-397B-A17B(397B / **17B 激活**) | MiniMax M2.7(230B / **10B 激活**) |
| **能力档位** | **最强**(开源权重第一梯队) | 强(通用推理明显高于 M2.7) | 顶配 agentic coding(专精) |
| **卡布局** | TP=2 × PP=6 = **12 卡** | TP=4 × PP=2 = **8 卡** | 每台 TP=4,共 8 卡(2 副本) |
| **权重(INT4)** | ~500GB,**12 卡勉强够** | ~200GB,8 卡轻松 | ~115GB/副本 |
| **单路速度** | **最慢**(32B 激活 + 6 段流水线) | 中(17B 激活 + 2 段) | **最快**(10B 激活 + MTP) |
| **冗余容错** | ❌ 单故障域,一台宕全灭 | ❌ 单故障域 | ✅ 2 副本互备 |
| **复杂度** | **最高**(Ray + 6 段 PP 调优) | 高(Ray + 2 段 PP) | **最低** |
| **最大风险** | 稀疏优化 sm_86 是否掉慢速兜底 + 12 卡满载配电 | PP over 10GbE 延迟 | 6 卡闲置浪费 |
| **适合谁** | **要能力天花板,速度/冗余可牺牲** | **要强又要相对稳**(推荐的折中) | **求稳求快、先上线** |

**选型速记:**
- **★ 实际最推荐:方案二(397B)** —— 内核已被同族 122B 验证、8 卡就装下、速度和稳定性都好,是"更强单模型"里性价比最高的稳妥选择。
- **要榨干能力上限:方案一(K2.6)** —— 通用/agentic 能力最强,但要吃满 12 卡、6 段流水线、单路最慢,且它的注意力优化在 sm_86 能否不掉慢速兜底**必须先压测**。
- **求稳求快:方案三(M2.7)** —— 一周内上线、运维力量薄时首选;M2.7 专为 agentic coding 调优,**写代码这件事上未必输给更大的模型**,而且它最快、有冗余。
- **不想让推理跨 10GbE:备用方案四(8+6)** —— 8 卡机单机跑 397B,6 卡机跑 M2.7;强模型和快模型同时在线,但启用前必须确认第 8 张 A40 的插槽、供电、风道与拓扑。

> **反直觉但重要**:更大 ≠ 在写代码上更好。397B/K2.6 强在通用推理与长程规划;若你的负载几乎全是写/调 skill + 敲代码,M2.7(方案三)的速度 + 冗余可能体验更好。**建议三个都拉真实 agentic 任务实测再定。**

## 二、公共准备(所有方案都要做)

### 2.1 进场核对

```bash
nvidia-smi topo -m                                              # NVLink 桥拓扑,挑同根桥的卡组做 TP
nvidia-smi --query-gpu=power.limit,power.draw,temperature.gpu --format=csv
ip -br addr                                                     # 记下万兆光口接口名(PP 方案要锁它)
df -h ; lsblk                                                   # 权重务必落 SSD
lspci -nn | grep -i nvidia                                      # 8+6 前确认目标机能枚举 8 张卡
```

- **配电**:7×300W + 2×185W ≈ **2.5–3kW/台**。方案一(12 卡满载)、方案二(8 卡)都要确认 PSU 冗余 + 机柜配电(🔴 高风险项)。
- **散热**:A40 被动散热,确认 GPU 专用机型风道。
- **存储**:权重必须放 **480GB SSD RAID0**;K2.6 ~500GB 要确认盘够大。
- **拓扑**:TP 组挑同一 PCIe root、能两两搭 NVLink 桥的卡;出现 `PHB/NODE/SYS` 的别编进同一 TP 组。
- **8+6 物理门槛**:先向整机厂确认 8 卡机型支持。必须同时满足第 8 个双宽 PCIe 槽位、独立 8-pin 供电、GPU 风道/挡板、PSU 余量、BIOS `Above 4G Decoding` 和 8 卡枚举;不能只看主板还有一个槽就直接移卡。

### 2.2 环境

```bash
# 两台统一使用离线包内的CUDA 12.4镜像,不在宿主机pip安装vLLM/CUDA
nvidia-smi                                  # 驱动必须 >=550.54.15
cd /offline-xt
./scripts/install-offline.sh                # load并执行驱动/torch CUDA/A40完整验收
```

CUDA 12.4兼容边界:

- 宿主机只提供NVIDIA驱动和容器runtime,已安装的CUDA Toolkit版本不会挂入容器。
- `xt-vllm:0.24.0-cu124` 内的 `torch.version.cuda` 必须为12.4.x;Dockerfile构建时和现场安装时都会硬校验。
- `v0.24.0` 是待联网验证的占位tag。最终tag还必须同时支持三个模型架构、AWQ Marlin及对应tool/reasoning parser;验证后锁死镜像tar和SHA256,现场禁止pip升级。
- 两台的镜像ID、驱动生产分支、vLLM和Ray版本必须一致;跨机PP不允许混用不同镜像。

### 2.3 权重(离线包三套全备;服务器按最终布局选择落 SSD)

```bash
export HF_HUB_ENABLE_HF_TRANSFER=1
# 正式离线包以下三个全部下载;现场服务器只落盘当前布局需要运行的权重
# 方案一:Kimi K2.6(社区 AWQ/GPTQ INT4,现场确认可用量化)
huggingface-cli download <org>/Kimi-K2.6-AWQ            --local-dir /data/models/Kimi-K2.6-AWQ           # ~500GB
# 方案二:Qwen3.5-397B-A17B
huggingface-cli download QuantTrio/Qwen3.5-397B-A17B-AWQ --local-dir /data/models/Qwen3.5-397B-A17B-AWQ  # ~200GB
# 方案三:MiniMax M2.7
huggingface-cli download QuantTrio/MiniMax-M2.7-AWQ     --local-dir /data/models/MiniMax-M2.7-AWQ        # ~115GB
```

> **公共硬规则**:① 一律 AWQ **INT4**,❌ 不用 NVFP4(需 Blackwell);② KV `--kv-cache-dtype auto`,**A40 绝不开 fp8 KV**;③ MoE 一律加 `--enable-expert-parallel`;④ 简单调用 `enable_thinking:False`(对 Agent 延迟影响比任何参数都大)。

## 三、🥇 方案一:Kimi K2.6 · PP 跨机(能力天花板)

**模型**:Kimi K2.6,1T 总参 / **32B 激活**,MLA(可在 Ampere 跑),开源权重第一梯队、定位就是 agentic 智能体。**代价是它最重、最慢**。

### 3.1 卡布局(TP=2 × PP=6 = 12 卡)

INT4 ~500GB,8 卡(384GB)装不下,必须铺到 **12 卡**:每台 3 个流水线段 × TP=2,跨机只一个 PP 切点。

```
机器A: 卡0-1 | 卡2-3 | 卡4-5   → PP stage 0/1/2 (Ray head)
                              │ 10GbE 只搬一次层间激活
机器B: 卡0-1 | 卡2-3 | 卡4-5   → PP stage 3/4/5 (Ray worker)
两台各剩 卡6 → embedding / 热备
```

### 3.2 起 Ray 集群 + PP 服务

```bash
# 两台都先锁网卡到万兆光口(否则可能走千兆管理口,直接慢死)
export GLOO_SOCKET_IFNAME=ens6f0 NCCL_SOCKET_IFNAME=ens6f0 NCCL_IB_DISABLE=1

# 机器A(head),只暴露参与建模的 6 张卡:
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5 ray start --head --port=6379
# 机器B(worker):
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5 ray start --address='10.0.0.1:6379'

# head 上起服务(vLLM 经 Ray 铺 TP=2 × PP=6;TP 组自动留在同机)
vllm serve /data/models/Kimi-K2.6-AWQ \
  --served-model-name kimi-k2.6 \
  --tensor-parallel-size 2 --pipeline-parallel-size 6 \        # ★ 机内 TP=2,跨机 PP=6
  --enable-expert-parallel --quantization awq_marlin \
  --gpu-memory-utilization 0.92 --max-model-len 65536 --max-num-seqs 64 \
  --kv-cache-dtype auto --enable-prefix-caching --enable-chunked-prefill \
  --enable-auto-tool-choice --tool-call-parser kimi_k2 \       # parser 名以现场 --help 为准
  --trust-remote-code --port 8000
```

**关键调优**:① `NCCL_SOCKET_IFNAME` 锁万兆口,双光口做 **bond(LACP)**;② `--max-num-seqs` 尽量大——**6 段流水线气泡大,必须靠高并发填满**,低并发时单请求延迟很难看;③ 首次多机卡死开 `NCCL_DEBUG=INFO`;④ **上线前必测**:K2.6 的注意力优化在 sm_86 是否掉进慢速兜底(实测 tok/s,不行就退方案二)。

### 3.3 优 / 劣

- ✅ 单档能力最强;两台真正合体跑一个巨模型;12 卡吃满。
- ❌ 单路最慢(32B 激活 + 6 段 PP + 过桥);**单故障域**,任一台宕机整模型全灭;运维最复杂;500GB 装得紧、KV 空间偏窄。
- ⚠️ **值不值全看 3.2④ 的压测**——稀疏优化跑不顺就直接退方案二。

## 四、🥈 方案二:Qwen3.5-397B-A17B · PP 跨机(推荐的强)

**模型**:Qwen3.5-397B-A17B,**17B 激活**,Gated DeltaNet(与已验证的 122B 同族,内核最放心),INT4 ~200GB。**选型里"差 8GB 单机装不下"的那个,PP 把它复活。**

### 4.1 卡布局(TP=4 × PP=2 = 8 卡)

```
机器A 卡0-3  TP=4  ← 前半层 (PP stage 0, Ray head)
        │ 10GbE 只搬层间激活
机器B 卡0-3  TP=4  ← 后半层 (PP stage 1, Ray worker)
两台各剩 卡4-6 → embedding / 小模型 / 热备
```

### 4.2 起 Ray 集群 + PP 服务

```bash
export GLOO_SOCKET_IFNAME=ens6f0 NCCL_SOCKET_IFNAME=ens6f0 NCCL_IB_DISABLE=1

# 机器A(head):
CUDA_VISIBLE_DEVICES=0,1,2,3 ray start --head --port=6379
# 机器B(worker):
CUDA_VISIBLE_DEVICES=0,1,2,3 ray start --address='10.0.0.1:6379'

# head 上起服务:
vllm serve /data/models/Qwen3.5-397B-A17B-AWQ \
  --served-model-name qwen3.5-397b \
  --tensor-parallel-size 4 --pipeline-parallel-size 2 \        # ★ 机内 TP=4,跨机 PP=2
  --enable-expert-parallel --quantization awq_marlin \
  --gpu-memory-utilization 0.90 --max-model-len 65536 --max-num-seqs 48 \
  --kv-cache-dtype auto --enable-prefix-caching --enable-chunked-prefill \
  --enable-auto-tool-choice --tool-call-parser hermes \
  --reasoning-parser qwen3 --trust-remote-code --port 8000
```

**关键调优**:同方案一的网卡锁定 + bond + 加大并发;PP=2 只有 2 段,气泡比 K2.6 小得多,延迟更可控。

> **备选同速档**:**Llama 4 Maverick**(400B/17B,标准注意力、官方支持 A40、**原生多模态**)——速度与 397B 同档,要多模态可换它,但编码口碑弱于 Qwen。

### 4.3 优 / 劣

- ✅ 内核最放心(同族已验证);8 卡就装下,还剩 6 卡做检索/热备;单路比 K2.6 快、比 M2.7 慢;通用推理明显强于 M2.7。
- ❌ 仍是**单故障域**、单路慢于 M2.7、要维护 Ray 跨机。
- ⚠️ PP over 10GbE 的实测延迟需压测(锁万兆口后一般可接受)。

## 五、🥉 方案三:M2.7 双副本(最简最快最稳)

**模型**:MiniMax M2.7,230B / **10B 激活**,Lightning 混合注意力,专为 agentic coding 调优(SWE-Pro 56%)。不跨机、不 PP,每台各跑一个副本。

### 5.1 卡布局与启动(每台一个副本)

```
机器A 卡0-3 M2.7 TP=4 :8001   |   机器B 卡0-3 M2.7 TP=4 :8001   |   两台各卡4-6 空闲/热备
```

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 vllm serve /data/models/MiniMax-M2.7-AWQ \
  --served-model-name minimax-m2.7 --tensor-parallel-size 4 \
  --enable-expert-parallel --quantization awq_marlin \
  --speculative-config '{"method":"mtp","num_speculative_tokens":2}' \  # MTP 投机解码治单路慢,不吃卡;报错就摘掉
  --gpu-memory-utilization 0.90 --max-model-len 65536 --max-num-seqs 32 \
  --kv-cache-dtype auto --enable-prefix-caching --enable-chunked-prefill \
  --enable-auto-tool-choice --tool-call-parser minimax_m2 \
  --reasoning-parser minimax_m2_append_think --trust-remote-code --port 8001
```

### 5.2 负载均衡(nginx,最简;或 LiteLLM)

```nginx
upstream m2 { least_conn;
  server 10.0.0.1:8001 max_fails=2 fail_timeout=30s;
  server 10.0.0.2:8001 max_fails=2 fail_timeout=30s; }
server { listen 8000;
  location / { proxy_pass http://m2;
    proxy_http_version 1.1; proxy_set_header Connection "";
    proxy_buffering off; proxy_read_timeout 600s; } }      # ★ 流式 SSE 必须关 buffering
```

```bash
nginx -t && nginx -s reload        # 原生nginx部署时入口为 :8000
```

离线包的 `./run.sh lb-nginx` 使用容器运行nginx,会把容器内`:8000`映射到宿主机`:9000`,避免和同机M2.7副本的`:8000`冲突;此时Agent统一连接`:9000`。

### 5.3 优 / 劣

- ✅ 最简单、依赖最少、自带故障转移;单路最快(10B 激活 + MTP);**唯一有冗余**的方案;配电只点 4 卡/台,压力最小;agentic coding 专精。
- ❌ 能力档低于 397B/K2.6 的通用推理;无多模态;**6 卡闲置**(可在卡 6 补个 embedding 减少浪费)。

## 六、备用方案四:8+6 双层模型(397B 强模型 + M2.7 快模型)

**适用条件**:两台机器允许把一张 A40 从机器B移到机器A,形成 **机器A 8卡 + 机器B 6卡**。该方案不增加模型和离线包种类,继续复用 397B 与 M2.7 的 AWQ 权重。

> **离线包原则**:无论最终保持 7+7 还是调整为 8+6,都固定准备同一个完整包,内含 K2.6、397B、M2.7 三套权重。现场只改变权重落盘位置和启动命令;8+6 不需要重新打包,K2.6 继续保留用于恢复 7+7 后直接部署。

### 6.1 推荐布局

```text
机器A(8卡):卡0-3 = 397B PP stage 0 / 卡4-7 = PP stage 1
            单机 TP=4 × PP=2,强模型入口 :8000

机器B(6卡):卡0-3 = M2.7 TP=4,快模型入口 :8000
            卡4-5 = embedding / reranker / 小模型 / 热备
```

**为什么 397B 仍用 `TP=4 × PP=2`,而不是直接 TP=8**:A40 只有两卡 NVLink 桥,8 卡 TP 会在每层产生跨 PCIe/NUMA 的 all-reduce。单机两段 PP 可以把 TP 固定在拓扑更好的 4 卡组,PP 切点也从跨机 10GbE 变成本机 PCIe,通常更稳。现场可把 TP=8 作为对照压测,但不作为默认配置。

### 6.2 启动

机器A(8卡)单机启动 397B,无需 Ray 跨机集群:

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 vllm serve /data/models/Qwen3.5-397B-A17B-AWQ \
  --served-model-name qwen3.5-397b \
  --tensor-parallel-size 4 --pipeline-parallel-size 2 \
  --distributed-executor-backend mp \
  --enable-expert-parallel --quantization awq_marlin \
  --gpu-memory-utilization 0.90 --max-model-len 65536 --max-num-seqs 48 \
  --kv-cache-dtype auto --enable-prefix-caching --enable-chunked-prefill \
  --enable-auto-tool-choice --tool-call-parser hermes \
  --reasoning-parser qwen3 --trust-remote-code --port 8000
```

机器B(6卡)执行方案三现有的 M2.7 命令,只使用卡0-3:

```bash
./run.sh m2.7
```

离线脚本快捷入口:

```bash
# 机器A(8卡)
./run.sh 397b-8gpu
# 机器B(6卡)
./run.sh m2.7
```

### 6.3 blade_agent 路由建议

| 请求类型 | 默认模型 | 原因 |
| ---- | ---- | ---- |
| 架构设计、复杂推理、长程规划、疑难代码审查 | `qwen3.5-397b` | 通用推理与规划能力更强 |
| 高频工具循环、写/改 skill、常规编码与补丁生成 | `minimax-m2.7` | 10B 激活,延迟更低 |
| 任一服务器故障 | 路由到仍存活的模型 | 不保证同模型冗余,但不会像跨机 PP 一样两台任一故障就全停 |

若 blade_agent 只能配置一个 OpenAI 入口,可用离线包中的 LiteLLM 配置暴露两个 `model_name`,由任务侧显式选择;不要把两个不同模型当作同一模型做随机负载均衡。

### 6.4 优 / 劣

- ✅ 397B 数据面完全留在单机,消除跨服务器 10GbE PP 延迟与 Ray 跨机依赖;397B 与 M2.7 同时在线,覆盖“能力”和“速度”两档。
- ✅ 任一机器宕机时另一档模型仍可服务,业务连续性强于方案一/二的跨机单实例;两个剩余 GPU 可承载 embedding/reranker。
- ❌ 两个模型都只有单副本,不等于同模型高可用;397B 的本机 PP 仍需按 `topo -m` 选择两个 4 卡组。
- ❌ 改卡涉及停机和硬件风险;8 卡机功耗、供电线束与风道压力高于原 7 卡配置。

## 九、进场执行顺序(建议)

1. **公共准备**(第二节):核对配电/拓扑/存储/网卡名 → 装 vLLM+Ray → 下权重。
2. **先落方案三**(最快见效、验环境):起 M2.7 TP=4,验 Lightning 内核 sm_86 无报错、开 MTP 压测单路 TPOT。以它作为**能力/速度基线**。
3. **要更强再上 PP**:
   - 先跑 **方案二(397B)** 打通 Ray 跨机 PP,压测 PP over 10GbE 延迟能否接受。
   - 若还要榨能力上限,再试 **方案一(K2.6)**,重点压测稀疏优化在 sm_86 的实测 tok/s。
4. 三者用**真实 agentic 任务(写/调 skill + 敲代码)横向对比**,连同 `enable_thinking` 开关的延迟差,定稿。
5. 若确定启用 **8+6 备用布局**,先完成整机厂确认和停机硬件检查,再移卡;启动 397B 单机 TP=4×PP=2 + M2.7 TP=4,最后验证 blade_agent 双模型路由与单机故障降级。
